# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Maintainer activity | Repo-facts block: latest release date, maintainer first-response sample, and recent repository activity | Pass if the latest release is within 90 days OR at least one owner/member/collaborator in the maintainer first-response sample responded within 60 days. If neither type of evidence is available, grade unclear. | required |
| Repository activity | Repo-facts block: dates of the last 5 default-branch commits | Pass if at least 2 of the last 5 default-branch commits occurred within the last 90 days. | required |
| Manageable scope | Issue body, labels, and comment thread: stated problem or goal, observed and expected behavior, concrete examples, blockers, unresolved decisions, and maintainer clarification | Pass if the issue describes one coherent bug or feature and gives enough evidence to understand what outcome would resolve it. A reproducible bug with clear observed behavior may pass even if the implementation approach is not specified. Multiple possible causes, possible fixes, files, or implementation steps do not make the issue too broad when they address the same underlying problem. Fail if the issue combines unrelated goals or leaves a required product decision, asset, specification, or external prerequisite unresolved such that the issue cannot be completed without additional direction. If the desired outcome itself cannot be determined, grade unclear. | required |
| Unclaimed issue | Repo-facts block: current assignees and linked PRs; comment thread in chronological order: explicit claim commands, bot/maintainer responses, statements that work is underway, and later unassignment/release messages | Start with repo facts: fail if there is any current assignee or open linked PR. Otherwise, read claim/work events in chronological order and use the latest relevant state. An explicit claim command such as `@zulipbot claim`, a confirmed claim, or an explicit statement that work is underway sets the state to claimed. The state returns to available only if later evidence explicitly rejects the claim, unassigns the contributor, releases or expires the claim, or states that the work was abandoned. Do not infer that a claim expired merely because it is old or because much time has passed. Expressions of interest without a formal claim do not set the state to claimed. Pass only when the final claim/work state is available. | required |
| No unresolved formal claim | Comment thread in chronological order: explicit claim commands such as `@zulipbot claim`, followed by any bot/maintainer rejection, unassignment, expiration, release, or abandonment message | Pass if there is no explicit formal claim command, OR every formal claim command is followed later by evidence that the claim was rejected, unassigned, expired, released, or abandoned. Fail if the latest formal claim command has no later clearing message. Do not treat age alone as clearing a claim. Expressions of interest such as "I'd like to work on this" are not formal claims. | required |
| Beginner guidance | Issue body and comment thread: reproduction steps, file/module hints, expected behavior, or maintainer implementation guidance | Pass if the issue provides at least one concrete starting point such as reproduction steps, an affected file/module, expected vs. actual behavior, or implementation guidance. | preferred |

## Verdict rule

Accept the issue only if every required check passes. Reject the issue if any required check fails. Treat `unclear` on a required check as a failure because missing evidence can create substantial risk for a first contribution. Preferred checks never change accept or reject; use them only to rank issues that already pass every required check.
